# Production Deployment Guide

## Architecture

```text
Vercel static frontend -> Render Express API -> managed PostgreSQL -> Prisma
```

The browser receives only `FRONTEND_API_URL`. Database credentials, JWT secrets, and AI keys remain on the Render service.

## Frontend: Vercel

`vercel.json` deploys the static `frontend/` directory. Set `FRONTEND_API_URL` in the Vercel project environment to the public API URL ending in `/api`, for example `https://lycan-internship-api.onrender.com/api`.

The build writes that public value to `frontend/runtime-config.js`. It must never contain API keys, database URLs, or JWT secrets. The dashboard, login card, and registration card all use the same API client configuration.

## Local PostgreSQL

For a local database, install Docker Desktop and start the supplied service:

```bash
docker compose up -d postgres
```

Then set the following values in `backend/.env`:

```env
DATABASE_URL=postgresql://lycan:lycan_local_only@127.0.0.1:5432/lycan_matcher?schema=public
JWT_SECRET=replace-with-a-long-random-local-secret
```

Run `npm run db:migrate`, `npm run db:seed`, and `npm run dev` from the repository root. The Docker password is deliberately local-only and must never be used for a hosted database.

To verify migrations locally, start the supplied PostgreSQL service and apply the committed migration history:

```bash
docker compose up -d postgres
npm run db:migrate:deploy
```

`prisma migrate diff --from-migrations` requires a real shadow PostgreSQL database, so it is not a placeholder-only validation command. `prisma validate` is used for schema validation; `prisma migrate deploy` is the safe migration command for local and hosted databases.

## Backend: Render

`render.yaml` defines the Express service. Create a Render Blueprint from this repository, then set the following values in Render:

- `DATABASE_URL`: PostgreSQL connection string from Neon or Supabase
- `FRONTEND_ORIGIN`: deployed Vercel origin, with no trailing slash
- `JWT_SECRET`: generated by Render or replaced with a long random secret
- `OPENAI_API_KEY`: optional; leave empty to use deterministic matching
- `CV_UPLOAD_DIR`: leave at its default only for temporary testing; configure durable private object storage before accepting real CVs

The Render start command applies the committed Prisma migrations before the API starts. Render supplies `PORT`; the API listens on that port and performs graceful shutdown on deployment termination. `GET /health` is a liveness endpoint. `GET /api/health` also verifies database connectivity without exposing connection details.

On a new, empty demo database only, seed the sample records once:

```bash
SEED_DEMO_DATA=true NODE_ENV=production npm --prefix backend run seed
```

The seed command deliberately clears its target database. Never run it against a database containing real users or applications. For an existing production database, deploy only with `npm run db:migrate:deploy`; do not use `prisma migrate dev`, `prisma db push`, or any reset command.

## CORS, Security, and CV Privacy

Set `FRONTEND_ORIGIN` to the exact Vercel origin, for example `https://your-project.vercel.app`, with no trailing slash. Multiple explicitly approved origins can be comma-separated. Do not use a wildcard origin in production.

The API applies baseline security headers, disables Express fingerprinting, rate-limits authentication attempts per process, validates JWT roles on protected routes, and logs only safe request metadata for server errors. The in-memory rate limit is appropriate for a single Render instance; move it to a shared store before horizontal scaling.

CVs are personal data. They are stored outside the public static directory and may be downloaded only by the owning student, an authorized recruiter with an application for that student, or an admin. Render’s local disk remains ephemeral, so this implementation is suitable for demo data only. Before accepting real candidate documents, replace it with private object storage, use signed URLs or authenticated streaming, define retention/deletion policy, and complete nDSG/GDPR review.

## Production Checklist

- verify `npm run db:migrate:deploy` succeeds against the hosted PostgreSQL database
- seed non-sensitive demo records only, and only on an empty database
- set production CORS origin
- run API tests
- run frontend build
- verify `GET /health` returns `status: ok`
- verify `GET /api/health` returns `status: ok` after PostgreSQL is connected
- verify login, application status update, notification, and CV flows against deployed services

## Release Checklist

1. Run `npm test` and `npm run build`.
2. Run `npm run db:migrate:deploy` against a disposable local PostgreSQL database or the empty hosted database.
3. Configure Render secrets and deploy the API.
4. Open `https://<render-service>/health` and `https://<render-service>/api/health`.
5. Configure Vercel `FRONTEND_API_URL` with `https://<render-service>/api` and deploy frontend.
6. Update Render `FRONTEND_ORIGIN` with the Vercel URL, then redeploy.
7. Test student and recruiter login, internship creation, application, status update, notification, protected CV access, and logout in the deployed browser.
8. Roll back by redeploying the previous Git commit. Do not roll back database migrations by deleting data; create an explicit forward migration when needed.
